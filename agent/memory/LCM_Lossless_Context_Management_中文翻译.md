## 摘要

我们提出**无损上下文管理**（Lossless Context Management, LCM）——一种用于 LLM 记忆的确定性架构，在长上下文任务上优于 Claude Code。以 Opus 4.6 为底座进行基准测试时，我们经 LCM 增强的编码智能体 Volt 在 OOLONG 长上下文评测中取得了高于 Claude Code 的分数，并且在 32K 至 1M token 的**每一个**上下文长度上都领先。

LCM 既可被视作对递归语言模型（Recursive Language Models, RLM）所开创的递归范式的一种验证，也可视作其扩展。我们的结果表明，递归式上下文管理能力不仅能够超越常规 LLM，还能超越具备原生文件系统访问权限的前沿编码智能体。

LCM 与 RLM 的区别在于：它把符号递归分解为两种由引擎管理的确定性机制——**递归上下文压缩**（层次化摘要 DAG 自动压缩较旧的消息，同时保留指向每一条原始消息的无损指针）与**递归任务划分**（由引擎管理的并行原语如 LLM-Map 取代模型自己编写的循环）。这种取舍类似于编程语言设计中从 GOTO 走向结构化控制流的转变：牺牲最大的灵活性，换取终止性保证、短任务上的零开销连续性，以及对所有历史状态的无损可检索性。

## 1 引言

大语言模型（LLM）的有效上下文窗口仍是复杂、长时程智能体任务的主要瓶颈。即便是拥有 100 万以上 token 窗口的模型，也不足以支撑长达数天的智能体会话——工具调用、文件内容与中间推理的量级会超出任何生产级 LLM 的上下文上限。此外，“**上下文腐烂**”（context rot）[1] 使问题进一步恶化：模型性能在远未达到标称上限时就开始下降。

Zhang 等人的递归语言模型（RLM）[2] 开启了一个重要的新范式：让模型主动管理自己的上下文，把提示词视作外部环境的一部分而非固定输入。在 RLM 范式中，模型获得一个 REPL，负责编写脚本来管理、切分并递归处理自己的上下文。“上下文管理可以是主动过程而非被动过程”这一核心洞见具有奠基意义。我们的工作建立在这一洞见之上，并致力于拓展其设计空间。RLM 探索的是该空间的一端：通过符号递归把记忆策略的完全自主权交给模型；我们探索另一端：如果由引擎代替模型管理记忆，并使用同样基于主动上下文管理理念的确定性原语，会发生什么？

我们的方法源于一个现实考量：完整的符号递归在生产环境中面临显著挑战。当让 LLM 编写管理其记忆的循环时，系统会继承模型的随机性——同一次 rollout 中高效的切块脚本，下一次可能就变得次优。此外，把每一次交互都包裹在递归脚手架中会带来“**短上下文惩罚**”：绝大多数本来就能轻松装进标准窗口的用户查询，也要额外承担延迟与成本。

表达能力与可靠性之间的张力，呼应了编程语言设计中的一个古老教训。早期程序使用不受限制的 GOTO 来实现任何想要的控制流，灵活性达到极致，但难以推理且容易出现隐蔽 bug。Dijkstra 的里程碑式批评 [3] 推动了结构化编程运动，用受约束的原语（for、while、if/else）取代 GOTO——这些原语在理论上表达能力更弱，在实践中却可靠得多。类似地，RLM 赋予模型类似 GOTO 的能力，可以使用任意控制流与上下文管理策略；LCM 则提供结构化控制流的等价物：一小组定义良好的算子，确定性地覆盖常见场景。

具体而言，LCM 把记忆架构的负担从模型移回引擎。它不要求模型发明记忆策略，而是提供确定性的、数据库支撑的基础设施：在一个持久化事务型存储中维护高扇出的摘要 DAG，使系统能够激进地压缩上下文，同时保留指向原始数据的“无损”指针。

此前的 RLM 基准主要与原始基座模型对比；我们则用 Claude Code [4] 这一更贴近生产场景的强基线来评估 LCM。Claude Code 代表当前生产级智能体的最高水平，具备原生文件系统访问能力与工具能力。我们在 OOLONG 基准 [5] 上的评估表明，LCM 在长上下文聚合与推理任务上显著优于 Claude Code。这些结果直接反驳了“递归上下文管理不过是另一个 Claude Code”的常见说法。事实是：LCM 优于 Claude Code，因为 LCM 的递归架构在根本上更强大。

> **图 1 | 在 OOLONG-synth 长上下文基准上，带 LCM 的 Volt 对比 Claude Code。** 该图展示两者在不同上下文长度下相对原始 Opus 4.6 的提升幅度；正文指出：8K 与 16K 时 Claude Code 略有优势（+13.1 对 +11.2、+26.3 对 +25.0），从 32K 起 Volt 在每一个测试长度上都领先，并在 256K/512K 处拉开到 10.0/12.6 分的差距。

## 2 无损上下文管理架构

LCM 与常规压缩或滑动窗口方法的根本区别在于：它基于**双状态记忆架构**——**不可变存储**（Immutable Store）与**活动上下文**（Active Context）——保证无损可检索。所谓“无损”，是指会话中产生的每一条消息 m，其未经摘要的原始文本都逐字保存在不可变存储中，并可通过 `lcm_grep` 或 `lcm_expand` 到达。系统的设计目标是让智能体能够导航并恢复任何先前的状态，但我们无法确定性地保证智能体一定这样做。

不可变存储是唯一事实来源：会话中产生的每一条用户消息、助手回复与工具结果都逐字持久化、永不修改。活动上下文则是每一轮实际发送给 LLM 的窗口，由近期原始消息与预计算摘要节点混合组装而成；摘要节点是通过 LLM 摘要从较旧消息中派生出的压缩表示。摘要节点相当于不可变历史之上的**物化视图**：它们是派生缓存，不可变历史始终是唯一事实来源。由于底层消息始终保留，任何摘要都可以通过 `lcm_expand` 工具（附录 C）替换回原始内容。为防止上下文被淹没，`lcm_expand` 被限制在子任务中使用；主用户交互循环只能观察摘要，不能就地展开。

### 2.1 层次化 DAG

LCM 的核心数据结构是维护在持久化存储中的**有向无环图**（DAG），该存储支持事务写入、外键完整性与索引搜索。具体存储后端只是实现细节：我们的参考实现使用嵌入式 PostgreSQL 实例，但架构本身只要求具备上述性质。随着活动上下文窗口被填满，较旧的消息被压缩进**摘要节点**，而原始消息逐字保留。

这种基于 DAG 的架构克服了更简单检索策略的缺陷。把完整对话持久化到平面文件并依赖精确匹配搜索（如 grep）虽然保留了事实来源，但要求智能体已经知道自己要找的子串，对“到目前为止做了哪些架构决策？”这类开放式查询无能为力。基于嵌入的语义搜索（RAG）能处理开放式查询，但返回的是去上下文化的片段——谁在回应什么时说了什么、之后又决定了什么，这些赋予片段意义的结构信息被剥离了。层次化 DAG 同时解决两者：摘要节点提供会话历史的多分辨率地图，其下方的无损指针支持定向下钻到完整的原始上下文。

我们也可以在摘要节点或叶子消息之上加入嵌入索引作为补充检索通路；目前尚未实现，因为在我们的评测负载中，对事实来源做正则搜索并结合层次化摘要遍历已经足够。

为保证可靠性，LCM 采用确定性的、引擎驱动的控制循环（图 2），用软阈值（$\tau_{soft}$）与硬阈值（$\tau_{hard}$）来决定何时摘要。

**算法 1：LCM 上下文控制循环**（原文图 2）

```
输入: 新条目 h, 存储 D, 活动上下文 C
 1. 将 h 连同元数据（角色、token 数、时间戳）持久化到 D
 2. 将 h 追加到 C（作为指针）
 3. 若 Tok(C) > τ_soft:
 4.     触发异步压缩（不阻塞用户）
 5. 当 Tok(C) > τ_hard 时循环:
 6.     // 触及硬上限：阻塞式压缩
 7.     找出 C 中最旧的块
 8.     S ← EscalatedSummary(block)
 9.     用指向 S 的指针替换 C 中的该块
10. 返回更新后的 C 给模型
```

**算法 2：三级摘要升级**（原文图 3）

```
输入: 待摘要条目 X, 目标 token 数 T
1. 对 ℓ ∈ {1, 2, 3} 循环:
2.   若 ℓ = 1（常规）:
3.       S ← LLM-Summarize(X, mode="preserve_details", T)
4.   否则若 ℓ = 2（激进）:
5.       S ← LLM-Summarize(X, mode="bullet_points", T/2)
6.   否则:
7.       S ← DeterministicTruncate(X, 512)   // 不涉及 LLM
8.   若 Tokens(S) < Tokens(X):
9.       返回 S
10. 返回 S   // 第 3 级保证收敛
```

### 2.2 大文件处理

在智能体编码会话中，工具结果常常包含单个就接近甚至超过上下文上限的文件内容：一个巨大的日志文件、数据集或代码库 dump，一轮就能吃掉整个窗口。LCM 的解决办法是设定一个 token 阈值：低于阈值的文件正常纳入上下文；高于阈值的文件由引擎存放在外部，并在活动上下文中插入一个紧凑引用——一个不透明 ID、文件路径，以及预计算的**探索摘要**（Exploration Summary）。

探索摘要由一个类型感知的分发器生成，它根据文件类型选择分析策略：结构化格式（JSON、CSV、SQL 数据库）提取 schema 与形状；代码文件做结构分析（如函数签名、类层次）；非结构化文本则由 LLM 生成摘要。其结果是简洁的表示，让模型无需加载文件内容也能对其内容进行推理。

与逐字存放在不可变存储中的上下文消息不同，LCM 只保存文件路径的引用，文件内容完全留在文件系统上。这反映了一个生产级智能体会话的现实：被操作的文件（日志、数据集、构建产物）可达数十 GB，复制的代价高得令人望而却步。由于文件是异构的、有大量外部交互，通过标准文件系统操作（读取、grep、编辑）来处理它们最为合适——而智能体通过编码工具早已熟练于此。因此 LCM 的角色仅限于确保模型始终知道它遇到过哪些文件，文件操作则交给智能体已有的文件系统工具。

文件 ID 会沿摘要 DAG 传播：当引用某个文件的消息被压缩时，生成的摘要节点会保留该文件 ID。这保证即使经过多轮压缩，模型仍能知道并可以重新读取会话早期遇到的任何文件。

### 2.3 通过三级升级保证收敛

自主智能体中的一个已知难题是“**压缩失败**”：让模型摘要一段文本时，输出反而比输入更长。依赖模型生成控制流的架构（包括 RLM 式方法）必须考虑这种情况。

LCM 通过严格的**三级升级协议**（图 3）强制收敛：如果某一级摘要未能降低 token 数，系统自动升级到更激进的策略，最终落到不需要任何 LLM 推理的确定性兜底方案。

### 2.4 零开销连续性与确定性可检索性

两项架构不变量使 LCM 区别于递归式方法。

**零开销连续性。** 对 RLM 这类递归架构而言，一个实际问题是递归环境的“永远在线”特性：初始化 REPL、把提示词加载为变量、解释执行代码，即便对很短的交互也会引入延迟与成本。

LCM 在常见情形下完全规避这一开销。低于软压缩阈值 $\tau_{soft}$ 时，不发生任何摘要或存储检索：存储仅充当被动日志，用户感受到的就是基座模型的原始延迟。超过软阈值时，LCM 异步执行压缩，并在 LLM 轮次之间把结果原子地换入上下文。开销分为三种区间：

$$
\text{Overhead}(C)=
\begin{cases}
\text{none} & |C| < \tau_{soft}\\
\text{async} & \tau_{soft} \le |C| < \tau_{hard}\\
\text{blocking} & |C| \ge \tau_{hard}
\end{cases}
\tag{1}
$$

由于原子交换发生在轮次之间，除非在约 25 秒的压缩窗口内出现异常快速且 token 密集的连续提示与工具调用、从而突破硬阈值，否则用户感受不到额外延迟。实践中，这保证了在使用现代 LLM 的绝大多数软件工程工作流里，用户侧开销为零。*（译者注：原论文此处有脚注——压缩后的第一轮中，LLM 提供商必须为新插入的摘要以及压缩开始后进入上下文的消息重新生成 KV cache，因为它们不在上一轮的缓存里。不过摘要体积较小且替代了更大的旧消息块，而压缩后的消息本来也需要 prefill，因此额外延迟通常难以察觉。）*

**确定性可检索性。** 当 LCM 把较旧的消息压缩进摘要节点时，引擎会以编程方式、独立于模型输出地把被摘要内容的 ID 确定性地插入活动上下文，与摘要并列。这一后处理步骤由引擎强制执行。结果是：无论经过多少轮压缩，会话早期的任何消息总能通过 `lcm_expand` 工具无损取回。模型从不需要“知道”发生过压缩；它看到的只是带有稳定标识符标注的摘要文本，可按需展开。

**算法 3：LLM-Map 执行（引擎侧）**（原文图 4）

```
输入: 数据集 {x_i}_{i=1}^N, 提示词 P, Schema Σ, 并发数 N
 1. 初始化 worker 池（大小 N = 16）
 2. 对数据集中的每个 x_i 并行执行:
 3.     y_i ← LLM(P(x_i))
 4.     若 y_i 通过 Σ 校验:
 5.         标记 OK，存储 y_i
 6.     否则:
 7.         最多重试 K 次
 8.         若仍失败，标记 Error
 9. 结束并行
10. 在 LCM 存储中登记输出
11. 向智能体返回摘要句柄（Summary Handle）
```

### 2.5 集成：Volt

LCM 实现于 Volt 之中——一个以开源研究预览形式发布的 production 级终端编码智能体。Volt 从 OpenCode [6] 分叉而来：后者是一个开源、宽松许可、与提供商无关的编码智能体，基于 TypeScript 客户端/服务器架构与终端 UI 构建。选择 OpenCode 作为 Volt 的基础，是因为它功能完备且支持多种 LLM 提供商。在 Volt 中，LCM 引擎接管用户会话，替代 OpenCode 的默认会话管理。上下文控制循环与三级升级协议运行在 Volt 的消息处理流水线内，无需修改模型的工具定义或提示词格式。Volt 以开源研究预览形式发布，目的是使第 4 节的基准结果可复现，并支持对确定性上下文管理架构的进一步研究。

## 3 从符号递归到算子级递归

RLM 论文强调“**符号递归**”——模型编写循环的能力（例如 `for chunk in context: ...`）——是一种强大能力。这在最大化灵活性的同时，也要求模型在每次执行时正确用 Python 实现错误处理、并发与状态管理，从而在生产环境中引入波动。

### 3.1 算子级递归

作为 RLM 中模型生成循环的替代方案，LCM 通过两个工具引入**算子级递归**：LLM-Map 与 Agentic-Map。两者都把一个提示词并行应用到列表中的每一项。LLM-Map 把每一项作为一次无状态的 LLM 调用处理，适用于分类、抽取、打分等无副作用任务。Agentic-Map 为每一项启动一个完整的子智能体会话，可访问文件 I/O、代码执行等工具，适用于逐项处理需要多步推理或与环境交互的场景。

两种情况下，模型只需发起一次工具调用，迭代、并发与重试全部由引擎确定性处理（图 4）。这把“控制流”逻辑从随机层移到了确定性层。

这种设计使单次工具调用就能处理任意数量的输入，而模型完全无需管理循环或上下文窗口。

该设计的若干特性值得展开说明。

**数据库支撑的执行。** 引擎用持久化存储跟踪批次中每一项的状态：pending、running、completed 或 failed。并发 worker 通过悲观锁认领条目，保证恰好一次执行语义（出错重试除外）。失败项在标记为永久失败前会重试到可配置的上限。模型临时编写的脚本不太可能实现这些保证。

**基于文件 I/O 的上下文隔离。** `llm_map` 与 `agentic_map` 的输入列表和输出列表都是磁盘上的文件（JSONL 格式），位于活动上下文之外。这意味着模型可以处理任意规模的数据集，而输入或输出都不会污染或撑爆其上下文窗口。模型用常规编码工具（编写并执行脚本来抓取、过滤、格式化数据）组装输入文件，因此用户和父任务可以用自然语言表达“处理大数据集”的意图；智能体负责构造 JSONL 输入的机械工作，用户无需理解文件格式。

**Schema 校验的输出。** 每次工具调用都包含一个 JSON Schema，指定每个输出元素的预期类型。在每一次逐项 LLM 调用（对 `agentic_map` 而言是子智能体会话）之后，引擎按该 schema 校验响应。若校验失败，引擎会向该项的对话注入一条描述类型错误、要求修正响应的消息，重复至重试上限。这提供了一道类型级护栏：聚合结果的下游脚本可以依赖一致的结构，而无需对异构输出做防御性解析。我们承认，虽然已把 map-reduce 中的“map”一半实现为 LLM 驱动的算子，但尚未构建对应的 `llm_reduce` 或 `agentic_reduce` 工具。在我们的经验中，reduce 步骤通常由确定性代码更好地完成（模型编写脚本聚合带类型的输出），而不是再来一个 LLM 驱动的操作。构建 reduce 算子是对系统的直接扩展。

**递归组合。** `agentic_map` 子智能体是完整的智能体会话，可访问包括 `agentic_map` 自身的工具。这意味着：如果逐项工作需要自己的并行性，一次 map 操作可以递归派生嵌套的 map 操作。例如顶层对代码仓库做 map，每个仓库内部又对其文件做嵌套 map。在我们的使用中，这种递归组合运作顺畅，未出现无限递归行为——很可能是因为每一层嵌套操作的工作单元都严格变小。

### 3.2 防止无限委派

算子级递归解决了数据并行场景，但智能体系统还需要**任务委派**：派生子智能体来处理更大任务的一部分。子智能体对上下文隔离至关重要——中间工具调用对子智能体私有，为父智能体保留用于编排的上下文窗口。然而不受限制的委派引入了自身的递归风险：智能体可能把整个任务以完全相同的提示词委派给子智能体，后者再继续委派，产生一条永远不做实际工作的无限智能体链。

LCM 用一条**范围缩减不变量**来解决这个问题。当一个子智能体（而非根智能体）派生更下一级子智能体时，它必须声明两个参数：**委派范围**（delegated scope，即被交出去的具体工作切片）与**保留工作**（kept work，即调用方自己仍要完成的工作）。如果调用方说不清自己保留了什么（也就是打算把全部职责委派出去），引擎将拒绝该调用，并指示智能体直接完成工作。这迫使每一层委派都严格缩减职责，形成一种良基递归（well-founded recursion），最终必然落地到直接执行。

这条护栏有意在两种情形下不生效：根智能体（没有父级可与自己递归）与只读探索智能体（无法派生更多子智能体，因而无法递归）。它也不适用于并行分解——即智能体把工作拆成彼此独立的兄弟任务，因为兄弟式分解不会产生嵌套的委派链。

值得注意的是，与 RLM 通过固定递归深度上限防止失控执行不同，LCM 不需要这样的限制。范围缩减不变量提供了终止性的结构保证：由于每一层嵌套委派都必须严格缩减调用方的职责，递归是良基的，无论深度如何都必然触底。在我们的评估中，未观察到过度或失控委派的实例，证实了该不变量在实践中足够，无需人为设定深度上限。

**图 5 | RLM 与 LCM 方法对比。** 原文用代码展示两种写法：RLM 中模型自己写代码管理上下文（`for chunk in large_file: response = llm.query(chunk)`，完全自主）；LCM 中模型把控制流交给引擎，只发一次 `tool_call("llm_map", input_path="large_file.jsonl", prompt="Extract entities...", output_schema={...}, concurrency=16)`（确定性算子）。译者按：该图直观体现了全文的核心取舍——把循环从模型侧搬到引擎侧。

## 4 评估

我们在 OOLONG 基准 [5] 上评估 LCM，具体使用 `trec_coarse` 切分，测试长上下文推理与聚合能力。

### 4.1 基线

已有工作表明，在长上下文任务上递归智能体脚手架优于原始基座模型（如 GPT-5、Qwen）[2]。我们评估的是更新、更强的基座模型 Opus 4.6 [7]。为进一步定位性能，我们还对比了 Claude Code v2.1.4——一个具备原生文件系统访问与工具使用能力的成熟 CLI 智能体，作为代表生产级系统的更强基线。

在测试中，Volt 与 Claude Code 均以 Opus 4.6 作为主要推理模型 [7]。此外，两者都可使用 Claude Haiku 4.5 作为轻量辅助模型，用于逐项分类等高吞吐子任务。这保证任何性能差异反映的是架构选择，而非模型资源的不对等访问 [8]。

### 4.2 结果

> **图 6 | Oolong 基准上的性能。** 原文图注指出：LCM 通过确定性 map-reduce 工具而非线性上下文加载，优于 Claude Code，尤其在超长上下文区间。图中报告绝对分数；图 1 报告相对原始 Opus 4.6 的提升。

我们在上下文长度 8K 至 1M token 的 OOLONG 任务上评估了两个系统。图 6 报告绝对分数，图 1 报告相对原始 Opus 4.6 的提升。

平均而言，Volt 取得 74.8 的绝对分数，Claude Code 为 70.3，领先 4.5 分。相对原始 Opus 4.6 的提升幅度同样一致：Volt 平均 +29.2 分，Claude Code 平均 +24.7 分。

在较短上下文（8K 与 16K）上，完整输入可以轻松装进模型原生窗口，两者表现相当——Claude Code 在 8K（+13.1 对 +11.2）和 16K（+26.3 对 +25.0）略占优势。从 32K token 开始，Volt 在每一个测试长度上都超过 Claude Code。差距在 131K token 之后进一步拉大：256K 时 Volt 领先 10.0 分（+18.5 对 +8.5）；512K 时领先 12.6 分（+42.4 对 +29.8）；1M 时领先 4.3 分（+51.3 对 +47.0）。

未加任何智能体脚手架的原始 Opus 4.6 在超过 65K token 后急剧退化，在最大上下文长度下降到 20 分以下。

### 4.3 分析

结果揭示了两种不同的性能区间。在 32K token 以下，LCM 的确定性机制相对 Claude Code 的原生文件访问没有优势：两者都能把完整输入放进上下文，任务退化为直接推理。LCM 的**零开销连续性**（2.4 节）保证它在此区间不受惩罚，但也没有收益。

在 32K token 以上，两者分道扬镳，因为它们处理超出舒适上下文规模的输入时采用了根本不同的策略（图 5）。Claude Code 依赖模型自行设计并执行切分策略——通常是线性读取文件，或编写 Bash 脚本拆分处理。这种方式灵活，但引入两类错误来源：模型必须在每一次 rollout 中正确实现切分逻辑；还必须在自己的上下文窗口里跨块维持一致的状态。

相比之下，Volt 把迭代与聚合交给 LLM-Map，后者在模型上下文之外并行处理各项。模型从不接触原始数据集；它只指定逐项提示词与输出 schema，引擎返回聚合结果。这消除了上下文饱和作为聚合任务失败模式的可能，也解释了为何 Volt 的准确率在最大上下文长度上保持稳定甚至上升——额外数据提供了更多信号，却未给模型增加认知负担。

## 5 局限与未来工作

**OOLONG 中的数据污染。** 遵循 Zhang 等人的做法，我们采用 OOLONG 作为主要评测套件。然而，检查 Opus 4.6 的推理轨迹发现，模型偶尔会识别出底层数据，并直接从参数化记忆中给出正确答案，而没有执行要求的聚合。鉴于该基准公开可得，这并不意外，但会使结果解释复杂化。我们的处理方式是：排除所有推理轨迹显示出记忆迹象的任务，第 4 节只报告去污染后的结果。

为透明起见，我们在附录 A 中给出完整的去污染前结果。总体结论不变（Volt 在各上下文长度上均优于 Claude Code），但差距缩小。一个有趣的观察是：LCM 的架构似乎能部分隔绝污染效应——由于 LLM-Map 把各项作为独立分类调用分发，即便模型表现出识别数据集的迹象，结构上也会推动它走向逐项推理。而在单一上下文窗口内处理各项的系统，则为参数化捷径影响输出提供了更多机会。

对原始模型基线需附加一点提醒：我们的去污染流程依赖结构化推理轨迹来检测记忆，而无脚手架的模型输出没有这种轨迹。由于 Claude Code 与 Volt 都是与同一原始基线对比，基线中任何未被检测到的污染会同等影响两者的相对分数，我们认为这不会改变比较结论。

**迈向抗污染评测。** 更广泛地说，我们的经历凸显了静态基准在评估长上下文系统时的脆弱性。任何固定数据集最终都会进入某个前沿模型的训练分布，而且随着提供商扩大数据采集规模，问题只会更严重。我们认为更持久的解决方案是**程序化生成的评测**：测试框架即时合成新的上下文窗口，并为之配上从参数化模板（分类、聚合、检索）中抽取、基于新采样分布的任务。这种做法除抗污染外还有一个附带好处：它能生成任意长度的上下文，而静态基准做不到。当前 OOLONG 套件上限为 1M token，而原始 Opus 4.6 的上下文窗口已经超过这一天花板。要让评测随上下文长度增长持续有效，就需要与之共同扩展的基准。

## 6 结论

RLM 与 LCM 代表 AI 系统工程设计谱系上互补的两个点。RLM 体现“**以模型为中心**”的观点：通过让模型充当通用计算机，最大化其自主性。LCM 体现“**以架构为中心**”的观点：为模型提供结构化原语，减少它必须做的决策。

通过保持“有主见”（opinionated）——借助 LLM-Map 与 Agentic-Map 等原语把控制流约束在一个狭窄、行为良好的模式子集内——LCM 缩小了模型的搜索空间。系统保持透明：短任务零开销，同时可确定性地扩展到海量上下文，并保证先前状态无损可检索。我们在 OOLONG 上的结果表明，以架构为中心的方法能为生产级聚合负载带来可靠性与成本优势。

我们承认，随着 LLM 能力增强，支持架构式控制流的理由可能会减弱。若模型能在每次 rollout 中可靠地生成正确、高效的记忆管理代码，符号递归的波动惩罚就会减小。然而，以架构为中心的方法的某些优势可能不随模型能力而消失，最突出的是**零开销连续性**——它是系统的结构性属性，而非对模型局限的押注。此外，即便两种方法最终在能力上趋同，LCM 的确定性算子也能让无限上下文架构更快地投入生产：团队今天就能交付可靠的上下文管理，而不必等待模型掌握管理自身记忆的元技能。

两种方法并非互斥。正如现代语言仍保留 GOTO，以应对结构化控制流不够用的罕见场景，未来的系统可以默认使用 LCM 的结构化算子处理大多数情形，同时在确定性算子被证明不足的特殊任务上保留完整的 RLM 式符号递归。

## 附录 B LCM 数据模型

为支持第 2 节描述的无损保证，存储层把不可变消息历史（Storage）与派生的摘要 DAG（Materialized Views，物化视图）分离。关键要求是：事务写入（保证压缩操作的原子性）、引用完整性（防止孤立的摘要）、索引全文搜索（支持 `lcm_grep` 工具）。参考实现使用嵌入式 PostgreSQL 实例，但任何满足这些性质的存储后端都足够。

**Messages 表（消息表）。** 完整保真地存储用户、助手与工具内容；包含索引全文搜索列，供 `lcm_grep` 使用。

**Summaries 表（摘要表）。**

- **叶子摘要**（Leaf Summaries）：对一段消息的直接摘要。
- **压缩摘要**（Condensed Summaries）：对多个已有摘要的高阶摘要，支撑 DAG 结构。
- **溯源信息**（Provenance）：维护到父消息或父摘要的引用完整性，防止上下文“孤儿化”。

**大文件。** 对超过 token 阈值（默认 >25K token）的文件采用基于路径的存储。这些文件从不直接加载进活动上下文，而是以一个 ID 和一个计算得到的“探索摘要”表示（由针对 SQL、JSON、代码等类型的专用探索器生成）。

## 附录 C 工具接口

LCM 通过三类工具向模型暴露能力：用于查询不可变存储的**记忆访问工具**、用于并行数据处理的**算子工具**，以及用于管理子智能体的**委派工具**。

### C.1 记忆访问工具

这些工具提供对不可变存储的只读访问，确保模型不会意外破坏自己的历史。

**`lcm_grep(pattern, summary_id?)`。** 在整个不可变消息历史中执行正则搜索。返回按当前覆盖这些消息的摘要节点分组的匹配结果，使模型能理解每个匹配属于会话的哪个区域。结果分页以防上下文被淹没。可选的 `summary_id` 参数把搜索限制在某个摘要范围内。主智能体与子智能体均可用。

**`lcm_describe(id)`。** 返回任意 LCM 标识符（文件或摘要）的元数据。对文件 ID，包括原始路径、MIME 类型、token 数，以及首次遇到该文件时生成的探索摘要（2.2 节）。对摘要 ID，包括摘要种类（叶子或压缩）、token 数、父指针与完整摘要文本。该工具让模型无需展开就能查看某个压缩引用代表什么。

**`lcm_expand(summary_id)`。** 把摘要节点展开为其组成消息，撤销创建它的压缩操作。由于展开可恢复任意大量的早期对话，该工具被限制为由 `Task` 工具派生的子智能体使用；主智能体不能直接调用。这一限制防止主交互循环中上下文无控制地增长。当主智能体需要检查被压缩的历史时，它把展开工作委派给子智能体，后者在自己的上下文窗口中处理展开内容，只返回相关发现。

### C.2 算子工具

这些工具实现算子级递归（3.1 节），让模型通过一次工具调用处理无界数据集，而迭代、并发与重试由引擎负责。

**`llm_map(input_path, prompt, output_schema, ...)`。** 把 JSONL 输入文件中的每一项作为一次独立的 LLM API 调用分发处理。引擎管理 worker 池（默认并发 16），按调用方提供的 JSON Schema 校验每次响应，并用校验错误信息反馈给失败项以重试。逐项调用不可用工具、无副作用；每次调用都是从输入到结构化输出的纯函数。结果写入 JSONL 输出文件并登记到不可变存储。该工具适用于分类、实体抽取、打分等高吞吐、无副作用任务。

**`agentic_map(input_path, prompt, output_schema, read_only, ...)`。** 与 `llm_map` 类似，但为每一项启动完整的子智能体会话，而非单次 LLM 调用。每个子智能体可访问工具（文件读取、网页抓取、代码执行），可执行多步推理。`read_only` 标志控制子智能体是否可以修改文件系统。输出校验与重试逻辑沿用 `llm_map` 的模式。当逐项处理需要工具使用或单条提示词无法涵盖的多轮推理时，适用该工具。

### C.3 委派工具

这些工具管理子智能体的派生与协调，在保持上下文隔离的同时实现层次化任务分解。

**`Task(prompt, subagent_type, delegated_scope, kept_work, ...)`。** 派生单个子智能体自主执行任务。子智能体获得自己的上下文窗口与会话；所有中间工具调用对其私有，只有最终答案返回父智能体。这为父智能体保留用于编排的上下文，而不被中间结果消耗。

`Task` 工具继承自 OpenCode 的子智能体机制，但为 LCM 引入了一项关键修改：无限递归护栏。当子智能体（而非根智能体）调用 `Task` 时，必须提供两个附加参数：`delegated_scope`（描述被交出去的具体工作切片）与 `kept_work`（描述调用方为自己保留的工作）。如果调用方说不清自己保留了什么（即打算把全部职责委派出去），调用会被拒绝，并被要求直接完成该工作。这迫使每一层委派都严格缩减范围，形成类似良基递归的自然触底条件。只读探索智能体免于该检查，因为它们无法派生更多子智能体，因而无法递归。

**`Tasks(tasks[])`。** 接受两个或以上独立任务描述的数组，作为并行子智能体执行。`Tasks` 并发派发所有子智能体并聚合结果，使父上下文免受中间杂乱信息污染。递归护栏不适用于并行任务，因为它们代表兄弟式分解（把工作拆成独立单元），而非嵌套委派。该工具是 Volt 新增的，目的是把并行工作分解推广为一等模式，与 `Task` 的顺序委派互补。

## 术语与背景速览（译者整理）

| 术语 | 含义 |
| --- | --- |
| LCM（Lossless Context Management） | 本文提出的无损上下文管理架构：引擎侧确定性记忆 + 摘要 DAG + 算子级递归 |
| RLM（Recursive Language Models） | 递归语言模型，让模型写 REPL 脚本主动管理自身上下文的前置范式 |
| Immutable Store / Active Context | 不可变存储（逐字保留全部历史，唯一事实来源）/ 活动上下文（每轮实际发给 LLM 的窗口） |
| Summary DAG | 摘要构成的有向无环图：叶子摘要直接压缩消息，压缩摘要再压缩摘要，形成多分辨率历史地图 |
| 物化视图（Materialized View） | 摘要节点的本质：由不可变历史派生的缓存，历史本身始终是事实来源 |
| $\tau_{soft}$ / $\tau_{hard}$ | 软/硬 token 阈值：软阈值触发异步压缩，硬阈值触发阻塞式压缩 |
| 三级升级（Three-Level Escalation） | 保细节摘要 → 要点摘要（目标减半）→ 确定性截断（512 token，无 LLM），保证压缩收敛 |
| LLM-Map / Agentic-Map | 算子级递归工具：前者逐项无状态 LLM 调用，后者逐项启动完整子智能体；并发与重试由引擎负责 |
| 范围缩减不变量 | `delegated_scope` + `kept_work` 必须声明，确保每层委派严格缩减职责，从而保证终止 |
| 零开销连续性 | 低于软阈值时存储只做被动日志，用户只感受基座模型延迟 |
| 确定性可检索性 | 引擎在摘要旁强制插入稳定 ID，`lcm_expand` 可无损恢复任意早期消息 |
| 上下文腐烂（Context Rot） | 模型性能在远未达到标称上下文上限时即开始退化的现象 |
| OOLONG / `trec_coarse` | 本文采用的长上下文推理与聚合基准及其切分 |
| Volt / OpenCode | 实现 LCM 的开源终端编码智能体 / 其分叉来源（TypeScript 客户端-服务器架构） |

**核心数字速记**

- 评测区间：8K–1M token；绝对分数 Volt **74.8** vs Claude Code **70.3**（+4.5 分）。
- 相对原始 Opus 4.6 提升：Volt 平均 **+29.2** vs Claude Code **+24.7**。
- 从 **32K** 起 Volt 在每个长度领先；256K 领先 10.0、512K 领先 12.6、1M 领先 4.3 分。
- 短上下文 Claude Code 略优：8K（+13.1 vs +11.2）、16K（+26.3 vs +25.0）。

- 数据污染处理：剔除推理轨迹显示记忆迹象的任务，附录 A 保留去污染前结果。
